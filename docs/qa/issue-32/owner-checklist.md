# Чек-лист владельца: ручная публикация и откат

**Issue #32 не разрешает deploy. Эти шаги не выполнялись. Merge ≠ deploy.**
`vk-cloud-staging` — имя environment; workflow пишет в **production bucket
`mythweld-web`**, который обслуживает работающий сайт.

## До отдельного разрешения — только подготовка

1. Проверить PR, зелёный CI и [QA-отчёт](README.md). Merge выполняет владелец.
2. Зафиксировать полный SHA кандидата из `main`, SHA предыдущей успешной
   публикации, URL её Actions run и доступный `dist-<sha>` (хранится 30 дней).
   `Last-Modified` и совпадение HTML не устанавливают deployed SHA; взять его из
   Summary «Deploying …» / истории deployments. Старый артефакт не является
   входом текущего rollback workflow: тот заново собирает выбранный коммит.
3. На Node 24 в чистом checkout кандидата выполнить:
   ```bash
   npm ci
   npm run verify
   npm run secrets:check
   npm run deploy:plan
   ```
   Проверить 10 основных URL + `404.html`, ровно 10 записей sitemap, отсутствие
   `/dev/`, шести legal-страниц и черновиков; `LEGAL`/`legal.pages.*` = `null`,
   store URL = `null`, `robots.txt` = `Disallow: /`. Не менять gates ради деплоя.
4. Прочитать [runbook, разделы 8–9](../../deploy-vk-cloud.md#8-деплой-и-smoke-тест).
   По коду подтверждены: только `workflow_dispatch`, проверка принадлежности SHA
   истории `origin/main`, `contents: read`, проверки до upload, ключи только у
   шага upload, запрет соседних бакетов, последовательные запуски workflow.
5. Владелец самостоятельно убеждается в доступности Actions и существующих
   protection rules environment: reviewer = владелец, branch = `main`;
   в корректности переменных endpoint/region/`STAGING_BASE_URL` и области
   существующего ключа. Значения секретов не открывать/не передавать агенту.
   Настройки кабинетов и фактические права ключа в Issue #32 **NOT VERIFIED**.
   Если условия не выполняются — остановиться и согласовать отдельную задачу.
6. Учесть: загрузка неатомарная, до 6 параллельных `aws s3 cp`; сортировка
   плана не является барьером между всеми ассетами и HTML. При частичном сбое
   возможна смешанная версия. Prune по умолчанию удаляет отсутствующие в
   выбранной сборке объекты, кроме `_astro/`; заранее оценить удаляемые страницы.
   `deploy:plan` проверяет только локальные файлы, не показывает удаляемые remote
   keys, не подтверждает права записи/удаления, доступность AWS CLI или кэш CDN.
7. Получить отдельное явное разрешение на публикацию конкретного SHA. B7 и
   публичный релиз остаются NO-GO до юридического решения; этот checklist не
   даёт разрешения публиковать legal или открывать индексацию.

## Только после отдельного разрешения на deploy

1. Actions → **Deploy to VK Cloud** → **Run workflow**, workflow branch `main`,
   `ref` = полный проверенный SHA. Оценить `prune` (обычно `true`, чтобы удалить
   устаревшие страницы). Не запускать одновременно другой deploy.
2. Дождаться успешного build job: verify, secret scan, dry-run и артефакт.
   Сверить SHA в Summary; только после этого одобрить environment job.
3. Дождаться upload и smoke. Любой FAIL — не считать публикацию успешной.
   403 допустим только на отсутствующих путях с фирменной двуязычной 404 и
   `noindex`; 403 на существующей странице/ассете — FAIL. HTTP → HTTPS — уже
   принятый долг; не начинать новый облачный аудит и не менять ACL.
4. `STAGING_BASE_URL` может указывать на website-host: его успех не доказывает
   состояние apex. Отдельно проверить HTTPS **`https://mythweld.com`**:
   ```bash
   node docs/qa/issue-32/production-qa.mjs
   ```
   Скрипт делает только HTTPS GET/HEAD, сохраняет статусы/выбранные заголовки и
   сравнение с локальным `dist/`. Просмотреть JSON: 10 страниц = 200, правильные
   локали/canonical, sitemap = 10, robots закрыт; 6 legal-URL отсутствуют.
   Не заменять исторический отчёт в репозитории без новой датированной записи.
5. Открыть 10 страниц: изображения/шрифты, меню, клавиатура и язык; отдельно OG
   на apex. Зафиксировать SHA, run URL, время, PASS/WARN/FAIL и решение владельца.
   Ожидание кэша документов `s-maxage=300` — до 5 минут при соблюдении origin
   headers CDN; это не измеренная гарантия. При расхождении сначала повторить
   GET после TTL. Purge/изменение CDN не разрешены этой Issue.

## Откат — только владелец при отдельной авторизации

1. Остановить новые публикации, записать сбой и выбрать **предыдущий успешный
   проверенный SHA из истории `main`**, сохраняющий robots/legal gates.
2. Actions → тот же ручной workflow на `main` → `ref` = этот SHA. По умолчанию
   `prune=true` удалит страницы, которых в нём не было; старые `_astro/` сохраняются.
   Убедиться, что verify/secret scan/dry-run старого коммита проходят. Если нет —
   остановиться, не отключать проверки и не переходить к ручной загрузке.
3. Сверить SHA и одобрить environment job, дождаться upload/smoke; затем
   перепроверить apex по ожидаемому набору страниц **этого SHA**, robots и legal.
   Старый коммит может иметь 6/8 URL: новый smoke/checklist нельзя механически
   применять как ожидание 10. Отдельно проверить удаление новых страниц.
4. Зафиксировать rollback run/SHA/время/результат. Это повторная сборка, возможны
   недоступность npm/GitHub, несовместимость старого workflow или частичная загрузка;
   мгновенный атомарный откат не гарантирован. Изменения DNS/CDN/S3 policies,
   secrets, отключение сайта и иные аварийные меры требуют отдельного решения.
