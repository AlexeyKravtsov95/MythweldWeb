# AGENTS.md — правила работы в MythweldWeb

Этот файл обязателен для всех AI-агентов и автоматизаций, работающих с репозиторием.

## Порядок чтения контекста

1. Сначала текущая GitHub Issue и этот `AGENTS.md`: границы задачи и действующие запреты.
2. Затем [карта архитектуры](docs/architecture.md), чтобы выбрать нужные пути и символы.
3. Читать только релевантные файлы и диапазоны; для release/production — [текущее состояние](docs/current-state.md), затем нужный раздел runbook или release gates. Полный аудит без задачи не нужен.
4. Локальные skills в `.agents/skills/`: `repo-navigator` — поиск кода; `session-handoff` — краткая передача результатов. Не загружать все документы автоматически.

## Язык общения

- Все объяснения, отчёты, описания Pull Request, ревью и комментарии к Issue пишутся **на русском языке**.
- Идентификаторы, код, комментарии в коде, имена веток и сообщения коммитов могут оставаться на английском.
- Пользовательские тексты сайта живут только в типизированных словарях `src/i18n/dictionaries/*.ts` (EN — по умолчанию, RU — перевод).

## Процесс

- Работа ведётся только по GitHub Issue и только в его рамках. Не расширяй задачу без согласования.
- Одна задача — отдельная feature-ветка (`feature/<issue-id>-<кратко>`) и небольшой Pull Request в `main`.
- **Агентам запрещено пушить напрямую в `main` и выполнять merge.** Merge делает владелец после ревью.
- Перед открытием PR локально выполни `npm run verify` (формат, `astro check` + `tsc`, сборка, тесты) — CI повторяет те же шаги.
- В описании PR: что изменено, результаты проверок, шаги проверки, скриншоты (если менялась вёрстка) и известные ограничения.
- Не отключай проверки, не ослабляй `tsconfig` и не удаляй тесты, чтобы «позеленить» CI.

## Границы проекта

- Сайт статический (Astro, `output: "static"`). В коде сайта нет backend, аккаунтов, БД, аналитики и установки cookies. Использование cookies и журналирование на уровне инфраструктуры требуют отдельной проверки.
- Не трогать другие репозитории (`ForeverJourneyWeb`, `TalentForge` и т. д.).
- Не изменять работающие поддомены `journal.mythweld.com`, `legal.mythweld.com`, `ota.mythweld.com`.
- Не менять DNS, CDN, облачную инфраструктуру, деплой и GitHub secrets без отдельной согласованной задачи.
- **Никаких облачных учётных данных, токенов и ключей** в репозитории, коде, CI и логах.

## Честность контента

- Не выдумывать скриншоты, иконки (в том числе иконки классов и талантов), интерфейсы приложений и аддонов, функции продуктов, статусы релизов, цифры и отзывы.
- Изображения — только оригинальные ассеты продуктов; пиксели не меняются (без перерисовки, ретуши, рамок-телефонов). Пока ассета нет — честный placeholder.
- Ссылки — только на существующие ресурсы. Неопубликованные ссылки магазинов не добавляются.
- Не публиковать sitemap и ссылки на страницы, которых нет.

## Дизайн-система

- Утверждённое направление: **Mythweld v3.2 — The Forge (Product First)**.
- Цвета, типографика, отступы, сетка и формы берутся из семантических токенов `src/styles/tokens.css`. Сырые hex-цвета в компонентах запрещены (исключение — `<meta name="theme-color">`); локальные размеры конкретного компонента допустимы, только если для них нет токена в шкале.
- Новый токен добавляется по смыслу (`--color-text-muted`), а не по внешнему виду (`--color-grey-2`), и покрывается тестом в `tests/tokens.test.ts`.
- Контраст текста ≥ 4.5:1, цели нажатия ≥ 44×44, видимый фокус, отсутствие горизонтальной прокрутки на 320 и 390 px (EN и RU).

## Локализация и маршруты

- `/` — английский (локаль по умолчанию, без префикса), `/ru/` — русский.
- Каждая страница существует во всех локалях; `<html lang>`, `<title>`, ровно один `<h1>` и навигация локализованы.
- Новые строки сначала добавляются в тип `Dictionary` (`src/i18n/types.ts`), затем во все словари — иначе сборка не пройдёт проверку типов.

## Технические правила

- Node.js — версия из `.nvmrc` (LTS 24). Зависимости фиксируются точными версиями, `package-lock.json` коммитится, установка — через `npm ci`.
- TypeScript в режиме `astro/tsconfigs/strictest`; `any` и `@ts-ignore` не используются.
- Тесты: `tests/*.test.ts` (Vitest). Smoke-тесты проверяют собранный `dist/`, поэтому перед `npm test` нужен `npm run build`.
